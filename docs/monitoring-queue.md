# 检测调度与公开页面容量说明

## 部署顺序

当前实现采用 Cloudflare Cron 每分钟唤醒、Queues 分配置执行、Supabase 持久化任务与历史。后台 `check_poll_interval_seconds` 是队列检测周期来源，范围 60～3600 秒。已有有效设置保留；缺失或无效时使用 1800 秒。Cron 每分钟唤醒不代表每分钟执行全部检测。

已经执行 `20261021010000_check_queue.sql` 和 `20261021020000_monitoring_shared_cache.sql` 的数据库，只补执行：

`supabase/migrations/20261021030000_check_queue_followup.sql`

不要重跑旧两份。新迁移补齐后台周期控制、任务完成与恢复、历史版本缓存等逻辑；上线前先在预发布验证并保留数据库备份。

部署操作按顺序进行：

1. 补执行上述 followup 迁移。
2. 创建死信队列和工作队列：`wrangler queues create check-cx-checks-dlq`、`wrangler queues create check-cx-checks`。
3. 部署主站，确认内部队列 API 可用、调度令牌已配置。
4. 按 `worker/wrangler.toml` 部署触发 Worker，沿用后台生成的 `SCHEDULER_TOKEN`，基础地址指向主站。
5. 停用仍调用旧批量同步接口的调度入口，检查新队列消费与历史落库。

本文档不代表这些线上操作已经执行。本轮不主动运行构建、部署、创建队列或线上 SQL。

## 检测任务的资源边界

队列消费配置为单条消息一项任务，最大并发 10。运行中的一轮未结束，不叠加创建下一轮。后台的旧 `max_concurrency` 不控制队列并发；调整队列并发需要修改 Worker 配置并部署。

| 200 个检测配置的周期 | 理论模型请求/日 | 30 天历史条数 |
| --- | ---: | ---: |
| 30 分钟 | 9,600 | 288,000 |
| 15 分钟 | 19,200 | 576,000 |
| 5 分钟 | 57,600 | 1,728,000 |
| 1 分钟 | 288,000 | 8,640,000 |

以上不含基础设施重试、通知和官方状态请求；若单轮执行超过设定周期，实际轮数会减少。200 个配置全部耗尽 45 秒超时、并发 10 时，纯探测耗时约 15 分钟。因此配置 60 秒周期不能保证每个模型每分钟都有一次结果。

模型检测异常作为正常健康结果保存；基础设施错误最多执行 3 次。数据库原子领取、租约、任务历史唯一键和事务完成用于防止重复历史与互相覆盖。队列消息允许重投，持久化 outbox 支持补偿投递。数据库事务无法覆盖外部模型调用或通知发送：外发成功后进程在落库前中断，恢复时仍可能再次外发。

已核对 [Supabase Cron 概览](https://supabase.com/docs/guides/cron) 和 [Quickstart](https://supabase.com/docs/guides/cron/quickstart)。Cron 基于 pg_cron，可直接执行 SQL/数据库函数，也可启用 pg_net 发起 HTTP 请求；不是只能调用 HTTP。官方建议并发 Job 不超过 8 个、单 Job 不超过 10 分钟。

Supabase Cron 可以替代 CF Cron 做单个轻量调度 Job，但不适合为 200 个模型各建一个 Job 或在数据库任务里等待全部外部探测。检测仍交给 Queue，主要模型调用负载不会减少。现阶段保留已配置的 CF Cron；若改用 Supabase Cron，应移除 CF 定时触发以只保留一个调度源。

Supabase Cron 的 Job 定义保存在 cron.job，运行记录保存在 cron.job_run_details，Dashboard 的 Job History 可查看。该运行记录不会自动清理，需要单独保留策略；HTTP 入队成功也不代表模型检测完成，最终结果仍以业务任务表为准。

## 首页访问不会触发检测

首页先返回页面框架，再请求公开配置、仪表盘、通知和调度状态。可见页面每 60 秒刷新仪表盘和调度状态；隐藏页面暂停自动刷新，同一页面不重叠请求，也不预取所有统计周期。

| 持续可见访客 | 仪表盘和状态 API 请求/分钟 | 平均请求/秒 |
| --- | ---: | ---: |
| 300 | 600 | 10 |
| 500 | 1,000 | 约 16.7 |

上述不含首屏 HTML、静态资源、通知/配置、手动操作和网络重试。访客数不乘到模型检测频率上。

公开响应通过 Cloudflare Cache API 显式缓存：仪表盘、分组、公开站点配置和通知 30 秒，调度状态 15 秒。浏览器每次验证，避免额外叠加浏览器缓存时间。先查边缘缓存，再处理 ETag，命中时不重新聚合。缓存键只使用已验证的周期和分组；随机 `_t`、`forceRefresh`、Cookie 不会生成新缓存键。管理、内部执行和鉴权接口不使用此缓存。

缓存只保存允许公开的 200 响应，排除 Set-Cookie、private、no-store 和 Vary 响应。缓存故障降级为原始加载。相同实例的同时回源会合并，并为每个调用方复制响应体。`X-Public-Cache` 为 `HIT`、`MISS` 或 `BYPASS`，便于上线检查；本地没有 Cloudflare Cache API 时为 BYPASS。

Cloudflare Cache API 按机房缓存，并非全世界只有一份。冷缓存、多个实例和多个机房仍可能同时回源；每个访问请求依然进入 Worker，不能把边缘缓存命中等同于 Worker 请求免费或数据库查询恒定只有一次。

服务端还有短时实例数据缓存和数据库共享 SLA 聚合缓存，用于减轻跨实例聚合。首页 HTML/SEO 的站点设置读取依赖已有实例缓存，没有被本轮 API 响应缓存覆盖。已有官方状态实例缓存也不提供跨实例强一致保证。

## 更新时效与上线观察

展示延迟由检测周期、任务排队/执行、数据缓存和可见页面刷新共同决定。公开 API 最多复用约 30 秒响应，部分底层缓存还有自己的有效期；不能承诺结果写入后一律 60 秒内可见。SLA 聚合缓存 60 秒，历史版本不变时可复用更久，最新健康状态与 SLA 汇总的时效也有差别。

上线后分别观察：

- 同一周期 API 的 `X-Public-Cache` 命中率和响应大小、延迟。
- Worker 请求数、CPU、子请求错误和队列最老消息年龄、重试、死信。
- Supabase CPU、连接数、慢查询、历史表增长和统计缓存命中。
- 200 配置的真实单轮完成时间，以及页面在实际设备上的数据解析和渲染耗时。

当前没有核实 Cloudflare 套餐额度，也没有做生产流量压测，不能保证免费额度足够或任意访客数量下零压力。缓存和队列先隔离两类负载，再用实际指标决定是否调整刷新周期、消费并发和响应体积。

## 后台日志入口

- `/admin/trigger-logs`：已有调度触发日志页面，支持分页、来源/状态筛选和手动刷新。队列模式每次新建检测轮次写入 worker_trigger_logs，检测结束回填耗时、检测数、异常数和汇总信息；每分钟没有新建轮次的唤醒不写入该表。不能凭一分钟没有记录判断 Cron 没有运行。
- `/admin/history`：已有各配置检测结果和延迟记录；模型检测结果正常落库后可查看。
- `check_queue_runs` 与 `check_queue_tasks`：保存整轮进度和任务状态、执行次数、最近错误及租约。当前未接入后台任务明细页面，需要通过受控数据库查询查看。
- Cloudflare Worker Logs：查看每次调度调用、消息消费异常、重试与终止失败。服务未触达或数据库不可用时，业务数据库日志可能不存在，应结合 Worker Logs 排查。

整轮日志结束表示检测任务结束，不表示告警、汇总等所有后续任务已成功；后续任务需检查任务表和对应告警历史。当前运行/任务详情默认清理已终结且无待执行任务的 3 天前轮次，排障时需留意保留窗口。

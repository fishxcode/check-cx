# 检测队列实施计划

目标：修复 Cloudflare 单次检测子请求超限，支持约 200 个配置，并控制数据库和页面访问成本。

架构：Cron 创建持久化计划，Queues 唤醒单配置任务；数据库原子领取与完成保证历史不重复。通知按渠道拆分；页面读取共享统计快照，不触发检测。

约束：不执行 build、不启动开发服务器、不新增测试文件；采用只读原型参考与独立审查，轻量类型检查和内存模拟验证。

- [x] 新增任务、运行记录与原子 RPC；租约恢复、有限重试、持久化 outbox、定期清理。
- [x] 实现任务接口及 Queue producer/consumer；并发 10，消息只包含任务 ID。
- [x] 独立通知与整轮收尾；旧同步大批接口明确拒绝超大请求。
- [x] 统计共享缓存、展示缓存短 TTL、隐藏页面暂停刷新，避免访问量放大聚合开销。
- [x] 审查、轻量验证并写清数据库迁移、Queue 创建及部署顺序。

容量基线：200 配置 × 48 轮/天 = 9,600 次检测/天；30 天约 288,000 条历史。并发 10，45 秒超时情况下单轮纯探测约 15 分钟，不承诺秒级故障发现。模型健康失败不做任务重试；基础设施失败最多 3 次。外部模型和通知不能通过数据库事务保证 exactly-once，必须明确极端中断时可能重发。

展示目标：结果落库后页面约一分钟级更新；SLA 统计与最新状态分别管理缓存，不能把采集间隔当展示缓存时间。实际延迟需上线测量。精确 p95 不能用分组 p95 平均代替。

部署状态：实现与本地验证已完成；线上增量 SQL、Queue 创建、主站与触发 Worker 部署尚未执行。部署步骤及容量边界见 `docs/monitoring-queue.md`。
